# Cavalry：原生复制、数据与共用控制

适用：在 Cavalry 中制作可编辑的程序化动效。重复对象使用原生关系，用户可在节点、数组和 Graph 中修改动作。不要把每个副本的运动都展开成独立关键帧，也不要为了少关键帧而堆出难读的数学网络。

## 跑通的路线：FAFA

**实跑记录：** 本机 Cavalry 2.7.2。构建步骤使用 Python 批量写入原生 `.cv` 节点和连接，Cavalry 界面负责打开、保存、显示与渲染；应用内小脚本用于读取属性定义或执行打开、渲染。成片播放使用原生节点，未使用运行时 JavaScript 绘图节点。复用这条路线前，确认用户允许这种制作自动化；它不能替代用户明确指定的纯 UI 绘制。

| 步骤 | 具体操作 | 成功标志；未达到时停在哪一步 |
| --- | --- | --- |
| 1. 确认基线与分镜 | 读取最新已确认 `.cv` 和当前源片区间；保留旧版供比较 | 已知当前末帧、已有分组与目标追加范围；不能只选名字类似的旧脚本 |
| 2. 读取原生样本 | 在本次样本工程中建立少量目标节点，读取属性定义；不猜枚举、数组条目类型和输入端口 | 得到应用返回的节点类型和属性定义，并能在画布显示一个母形与多个副本 |
| 3. 建立共享关系 | 用母形、Duplicator、数组与共用进度建立本段运动；再按实际需要补 Math | 改一个展开或速度控制，相关副本共同变化；各副本无需独立重做时间轴 |
| 4. 写入同一工程 | 将新节点、层级、连接与目标范围加入当前文件；保留原有文字、字体和后续分段 | 文件可读取；这些只是结构证据，下一步必须在应用中打开 |
| 5. 在 Cavalry 打开并保存 | 用 File → Open，或单独运行打开脚本；选择本段中间帧检查，再由应用保存 | 标题栏是目标文件，画面出现本段完整对象，原生属性可编辑；不是只看到母形 |
| 6. 单独渲染 | 打开动作结束后，用 Render Manager 或单独的 `api.renderAll()` | 输出文件更新时间改变，顺序解码得到完整范围，复制器的多个副本实际出现 |
| 7. 对照并修正 | 顺序解码源片与渲染，按相同时间检查方向、间距、数量、层距、转场 | 找到明确差异并修正后重新出图；例如中列首尾都补出圆，不能只看总节点数 |
| 8. 接续与交付 | 从最新确认文件继续下一段；输出独立成片、需要的对比和控制说明 | 本例最终得到同一合成的五段动画、359 个可解码帧；九种字体也在原生渲染中生效 |

只导出从第 6 步进入；只修改字体按“原生中文字体混排”处理，再走第 5–7 步。这里的帧数、复制数量和字号均是案例值，不是新工程模板。

## 碰壁与处理

| 碰到的现象 | 判断与处理 | 实际结果或证据边界 |
| --- | --- | --- |
| 同一脚本打开工程后立即渲染，画面只出现首个副本 | 先结束打开操作，确认当前文件；再单独渲染 | 分开调用后导出了完整副本。只证明本机这条处理有效，不推断其他版本必然有同样问题 |
| 工程文件写完、节点数正常，但无法检查画面 | 结构检查不能证明实际动画；恢复可用的应用操作后再打开和导出 | 早期未完成原生验证，后续恢复 UI 后完成了全片解码和画面对照 |
| `-10005` 超时后，不清楚操作有没有执行 | 重新读取界面和目标文件时间；确认状态后才重试 | 多次打开或渲染调用虽超时，文件实际已保存或输出；不能每次都重新触发 |
| `Cavalry --help` 打开了 GUI | 当前 GUI 程序不能据此作为 CLI 渲染命令 | 停止这条探测，使用原生打开与渲染入口，之后得到有效视频 |
| 中列展开后，底部出现空缺 | 只移动已有中列不足以还原数量变化；改成原有圆运动并补出首尾新圆 | 紧凑阵列最终使用十四个副本，逐帧图中上下两端都出现新增圆 |
| 可编辑文字全变成同一种大楷 | 仅保留了文本编辑能力，丢失字体类型差异 | 接入九种 Typeface、分段 Typeface Array 和字号比例数组；实际渲染确认混排 |
| 新字体在黄底圆阵中偏大 | 同字号下的可见字面不同；按字体调整比例数组，保留自然宽窄 | 再次原生渲染检查，修正过大字面，没有改圆阵的运动进度 |

**尚未确认的根因：** ScreenCaptureKit `-3811` 的故障原因未被证明。后续 UI 恢复并渲染成功，不代表已证明重启、等待或保持亮屏能根治它。遇到该错误，先判断当前能否读到应用画面；不能读取时明确还缺哪项证据，别重复同一无效操作。

**尚未完成的结构优化：** 最终网络仍含大量数学节点。已经跑通“原生可编辑”，并未证明它是最少节点或最佳性能方案。学习共享关系和构图控制，不照搬该网络规模。

## 先确定动作关系

在当前 `.cv` 工程中找到目标合成、分段和控制组。继续后续分镜时，保留同一个文件和已确认的部分。完整视频可以只有一个合成、多个分段组；分组和分镜不是合成数量。

先明确一个母形、复制方式及可调参数，再建立原生节点。按需要选择：

| 动作或内容 | 原生结构 |
| --- | --- |
| 重复字块、回声层、风车臂 | Text Shape / Shape 母形 + Duplicator |
| 副本之间的数值或时间错位 | Stagger 或副本上下文驱动的共享关系 |
| 时间映射到展开、转动、速度 | Frame / 合成时间 + Number Range 的 Graph |
| 每个副本不同的值或文字 | Value Array / String Array + 索引 |
| 同组混排不同字体 | Typeface + Typeface Array |
| 移动圆的外包络自动变化 | Convex Hull |
| 轮廓间连续过渡 | 满足拓扑要求的 Blend Shape |
| 组合少量数值关系 | Math / 向量运算，避免重复算相同进度 |

从用户能理解的参数组织控制，例如“行间距”“向两侧展开”“层间比例”“停留与回弹”。优先复用已有控制和软件内置分布；先做小范围可见动作，再扩展副本。

## FAFA 中有效的建模方式

### 字阵、递归方框和竖列

母形保留 Text Shape、纸片和色圆。让副本索引决定文字与配色，共享轨道控制位置。

沿闭合轨道流动时，保留位置相位的小数部分；只有换字编号需要取整。过早取整会使字块逐格跳动。字号、纸片尺寸、轨道间距和递归层距分开控制，否则修一个比例会同时改变运动。

竖列的冲出、停顿、再次推进和回弹需要完整速度曲线。只连接开头和结尾两点不能还原节奏。

### 圆阵与黄色包络

黄色外形由实际移动的圆驱动 Convex Hull。可将输入圆与可见文字圆分开，但二者共享位置和尺寸。

八圆菱形补成矩形，再向上下展开时，要区分“已有圆移动”和“新增圆出现”。曾出现只把中列上移、下方留下缺口的问题；修正为首尾新增圆与原有圆共同变化。新增数量和展开方向来自参考，不固定成所有圆阵的规则。

两个中心圆在分裂前重合时，重合副本应使用一致字形和位置。否则字体混排会在分开之前产生双重字影。

### 白底风车

红字和蓝字各用母形与复制器，共享展开、转动、补齐和重排进度。位置转动与文字自身朝向分开，避免参考中朝上的文字跟随轨道一起旋转。

控制“补齐副本”“沿轨道移动”和“字块重排”三个动作，不把它们揉成一条整体旋转。每段交接处检查数量、颜色、尺寸和位置。

## 原生中文字体混排

使用 Text Shape 保留直接改字能力。字体替换先确认字体族和样式都能被 Cavalry 找到，并用实际字表检查字形；系统里装了字体不等于应用中能正确渲染。

可用的字体检查接口在该案例中为：

```javascript
cavalry.fontExists(family, style);
cavalry.getFontStyles(family);
cavalry.measureText(text, family, style, fontSize);
```

使用当前 API 文档核对参数。不同字体的字号、行高、可见字面和中心可能不同。Pillow 样张可辅助选字体，最终大小以 Cavalry 渲染为准。

原生连接方式：

```text
Typeface.id → Typeface Array.array[n]
Typeface Array.id → Text Shape.typeface
```

Typeface Array 的 Auto Index 可按复制上下文分配字体；需要跟随换字时刻时，关闭自动索引并接入同一换字进度。并行建立字面比例 Value Array，使用相同的顺序和索引驱动字号缩放。

同字号的隶书、窄宋、粗黑和行楷可以保留自然的宽窄差异，只修正偏移、过大和溢出。不要重新收拢成一个字体，也不要强行把所有字体拉成相同长宽。

如果直接处理该版本 `.cv` 的 JSON，字体数组条目的 `varType` 是 `typeface`，字体节点的 `font` 值包含字体族与样式。这个格式来自本机样本，不是稳定的跨版本规范。优先通过应用建立少量样本后读取类型，再生成其余原生节点，并回到应用保存。

## 文字与回声轮廓的边界

FAFA 第二段曾将中心文字改为 Text Shape，外层回声保留 Editable Shape 与 Blend Shape。中心文字可直接改字，但外层轮廓不会随文本自动重绘。

这种结构必须说明修改范围。用户需要任意改字并同步改变回声时，应采用能由同一文字源驱动的结构；不能声称已有轮廓库支持所有文字。新字若超出轮廓库，修改对应形态或重建这段关系。

## 自动化建立原生工程

用户允许制作自动化时，可以批量建立节点或基于已确认的 `.cv` 样本生成原生连接。播放结果不应依赖外部构建脚本或运行时 JavaScript 绘图节点。

先读取当前工程与已接受的基线。旧的“追加第三段”脚本可能只写到第三段结尾；重跑它会丢掉后面的镜头或新加的字体。延续任务应从最新确认文件修改，不把历史构建器当作可无条件重复执行的总入口。

应用保存可能补齐默认属性和当前计算值。比较修改时区分用户设置、连接、Graph 与求值缓存，不能只对整个 JSON 做文本差异判断。

实际读取还遇到过没有 `attributes` 的内部节点。先按 `nodeType` 分类，再读取所需的合成或字体属性；不要假设每个 `hiddenFolder` 都具备普通图形节点的字段。

属性未知时，本案执行过下面的样本读取方式。`schemaPath` 绑定到本次可写 JSON 路径，在样本工程中运行，避免把探针混入交付画面：

```javascript
var face = api.create('typeface', '字体样本');
var definitions = api.getAttributes(face).map(function (attribute) {
    return api.getAttributeDefinition(face, attribute);
});
api.writeToFile(schemaPath, JSON.stringify(definitions, null, 2), true);
```

同样方式可读取本次已有节点的目标属性，确认后再接入生成器。不要从其他任务直接复制 `textShape#18`、旧节点 ID 或旧文件绝对路径。

用户只授权 UI 绘制时，以上文件生成方式不适用，使用当前可用的 Computer Use。

## 打开与渲染的具体顺序

本机跑通过两种打开入口：File → Open 选择 `.cv`，以及应用内打开脚本。脚本目录可通过 Scripts → Show Scripts Folder 获取，不能依赖作者机器的绝对目录。

已保存当前工作并确认目标文件后，第一次调用只打开和保存。示例中的路径与检查帧替换为本次文件和本段的一个可见帧：

```javascript
api.openScene('/absolute/path/project.cv', true);
api.setFrame(0);
api.saveScene();
```

调用结束，重新读到正确文件和画面后，第二次调用单独渲染：

```javascript
api.renderAll();
```

“分开调用”是实际步骤，不是在同一脚本中插入固定等待。当前已打开正确文件时不必再打开，直接确认范围后渲染。

若使用脚本菜单，只更新本次专用入口。不要覆盖用户已有的通用脚本或让一个叫“预览”的入口隐含重建旧工程。打开与渲染分开后，渲染入口应只处理当前工程。

检查渲染范围时分别读取合成末帧和队列范围，并用解码帧数确认端点约定。本例合成末帧为 358，最终导出 359 帧；不要把末帧编号当作总帧数。

## UI、捕捉和 CLI 问题

- `Computer Use server error -10005` 可能是读取超时。一次调用超时后，先重新读取界面和本次目标文件状态，确认操作是否已经执行，再决定重试。
- `ScreenCaptureKit ... Code=-3811` 曾阻止画面捕捉。若仍无法读取 UI，应明确缺少原生检查；不要靠重复“好了”、固定等待、不断重启或文件计数宣称恢复。
- 当前台应用变更或 AX 索引失效时，重新获取目标状态后操作。挂载的安装镜像与已安装应用可能重名，必要时使用已确认的完整应用路径。
- 本机案例执行 `Cavalry --help` 只启动了 GUI。不要把 GUI 主程序当作 CLI 渲染器。使用 CLI 前核对当前安装的真实可执行文件和当前官方支持；没有确认 CLI 时走已可用的原生 UI 渲染。

## 导出与统计

只导出时，保存当前文件并渲染所需范围，不重建工程。独立成片与左右对比视频分开交付。严格逐帧比较方法见 [参考拆解与对比](reference-video.md)。

需要统计时，使用 [cavalry_scene_report.py](../scripts/cavalry_scene_report.py)。只需 Python 3 标准库，读取 JSON 格式的 `.cv`，不启动 Cavalry、不修改工程。下列命令从技能根目录执行，输入与输出路径换成本次文件：

```sh
python3 scripts/cavalry_scene_report.py '/absolute/path/project.cv' \
  --output '/absolute/path/review/scene-report.json'
```

省略 `--output` 时报告写到标准输出。输出包含节点类型计数、连接数、活动合成、各合成的尺寸和帧范围、Typeface 定义；不存在的已保存属性显示为 `null`，不推断为零。该脚本已在 FAFA 当前工程中读出 1 个合成、33 个 Duplicator 和 9 个 Typeface。

按报告中的 `node_type_counts` 说明统计口径：

- `compNode` 是合成；`group` 不是合成。
- Number Range、Stagger、Blend Shape、Frame 属于 Behaviours；说明这是否是本次“效果器”的统计口径。
- Duplicator、Convex Hull、Math、各种数组分别计数。Effects 中的滤镜与着色器不要混入行为节点。
- `hiddenFolder`、材质和内部管理节点不等于用户实际添加的效果器。

报告中的字体定义不证明字体已经安装，文件结构也不证明应用已求值或渲染。不要把这份只读工具替换为旧 `append-rest.py` 或 `restore-font-variety.py`；这些构建器绑定旧快照、节点 ID 和本案字表，重跑可能覆盖后续工作。它们没有作为通用脚本打包。

2026-09-09 的 FAFA 完整文件包含 1 个合成、152 个行为节点、33 个复制器、3 个 Convex Hull、591 个数学节点。它证明原生连接已实现，但也说明数学网络较重。复用制作经验时应保留共享控制和原生关系，不照搬节点规模或把节点多当作使用了软件特性的证明。

## 案例证据与文档

FAFA 最终在同一个 `.cv` 中接续五段，使用九种字体混排，并完成 Cavalry 原生渲染与 359 帧解码。后两段接入时曾比较前三段 254 帧并确认一致；后来字体修改影响了画面，这条“像素一致”证据不能沿用到多字体版本。历史早期记录曾处于“文件已写但原生导出未验证”，也不能将早期状态沿用为后续结论。
